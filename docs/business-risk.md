# 비즈니스 리스크 — 가설 H1과 kill switch

> 심사(tech-critic-lead)에서 이 프로젝트는 **조건부 승인**됐다. 대체재(한컴 공식 뷰어, Google Drive/메일 내장 뷰어)가
> 요구 전체를 이미 커버하므로, "왜 새로 짓는가"의 우위 논거가 요구사항에 명시돼 있지 않다. 사용자에게 물을 수 없어(사용자 개입 금지),
> 아래를 **명제(fact)가 아니라 반증조건 달린 가설(hypothesis)**로 명문화한다.

## 가설 H1
> 한컴뷰어/Drive 대비 우리 뷰어가 "카톡 수신 → 열람"의 탭 수/전환 마찰을 유의미하게 줄이거나,
> "이미 설치돼 있고 로그인·광고가 없다"는 축에서 우위를 준다.

추론된 차별점(검증 대상, 아직 참이 아님):
- 한컴뷰어/Drive는 설치·로그인·광고·용량이 무겁다(추정).
- 여러 포맷을 각기 다른 앱이 열어 "받은 문서를 흘깃 보고 싶다"는 흐름에 앱 선택·전환 마찰이 있다(추정).
- 우리 것은 광고·로그인 없는 단일 경량 뷰어로 PDF/DOCX(→추후 HWP)를 한 자리에서 즉시 연다.

## Kill switch (정량 반증조건)
동일 카톡 수신 파일 기준, 다음을 **모두** 충족해야 H1 유지:
- 뷰어 화면 도달까지 탭 수가 한컴뷰어 경로보다 **최소 1탭 이상 적다**, 그리고
- **로그인 노출 0회, 광고 노출 0회**, 그리고
- 설치 무게(번들/설치 용량)가 한컴뷰어보다 가볍다.

미충족 시 → **H1 기각 → 프로젝트 재심사.**

경고(심사 지적): 한컴뷰어가 이미 설치돼 있으면 사용자에겐 "탭 수 동등 + 앱 하나 더 안 깔아도 됨"일 수 있다.
→ 진짜 승부처는 "이미 설치·로그인 0·광고 0". 축1 채점표는 탭 수만이 아니라 **로그인/광고/설치 무게**를 반드시 함께 채점한다([axis1-scorecard.md](axis1-scorecard.md)).

## H1은 Phase 1에서 완결되지 않는다 (중요)
한컴뷰어 대비 탭 수의 결정적 비교는 **실 Android 기기 + 카톡** 데이터가 있어야 발화한다.
이 개발 머신엔 Android 기기·adb가 없다.
- **Phase 1의 범위** = H1 판정에 필요한 **개발자측 데이터 수집**(인앱 파일피커 탭 수, 번들/설치 무게, 로그인·광고=0 설계 보장) **+ 사용자측(카톡 경로) 측정 프로토콜을 [user-intervention.md](user-intervention.md)에 인계**.
- Phase 1 종료 시 H1은 "판정 완료"가 아니라 **"판정에 필요한 데이터·프로토콜 확보 완료"** 상태다.
- 실세계 렌더 잔여 리스크(확보 불가 개인문서 코퍼스)도 이 문서에 기록해 이관한다.

## 스코프 재설계 리스크 (2026-07-21, 4포맷×폰·PC 전제 확정 후)
사용자 전제: ①폰·PC 둘 다 ②PDF/PPT/워드/한글 뷰어 열기 ③고화질 우선·저화질 허용 ④"바로 열기" 편의. 사용자 질문 불가 → 합리적 기본값 + 위험 기록.
- **RISK-A (iOS × 요구4 충돌)**: 전제①(폰 둘 다)과 요구④(바로 열기)를 iOS에서 동시 충족 불가(UTI/Document 등록 = Xcode+서명+개발자계정, CLI-only 위반). *기본값*: iOS는 "공유 → 뷰어" 수동 한 단계로 한정. 요구④는 **Android(intent-filter)+PC(file_handlers)로만** 충족 선언.
- **RISK-B ("저화질"의 과대해석)**: "저화질 허용"은 *고화질이 어려울 때의 폴백 허가*이지 "깨져도 됨"이 아니다. 확대 시 kill switch("한컴/파워포인트보다 나쁘지 않을 것") 직접 위반. *기본값*: 기존 실측 게이트를 PPTX/HWP에 동일 적용, 미달 포맷은 렌더 대신 **딥링크 폴백**.
- **RISK-C (HWP 포맷 비율)**: 실제 카톡 HWP 다수가 신형 .hwpx가 아니라 **구형 바이너리 .hwp**일 가능성 → "hwpx 우선" 가정 보류. *기본값*: 코퍼스에서 `.hwp:.hwpx` 실비율 먼저 측정 후 우선순위 결정.
- **RISK-D (미검증 토대 위 증축)**: H1은 여전히 UNVERIFIED(corpus-scorecard.json realCount=0). 검증 안 된 가치가설 위에 포맷 2 + 딜리버리 셸 2를 증축하면 실패 시 손실 배증. *기본값*: **P1 실코퍼스 + P2 file_handlers까지가 최소 안전 증축**, P3/P4는 축1·코퍼스 데이터가 말하기 전엔 착수 금지.
- **보안 표면 확대**: PPTX(pptxjs류)·HWP(hwp.js) JS 파서 = 신뢰 불가 입력을 먹는 zip/XML/바이너리 파서 추가 → 보안 하드게이트 6종(zip bomb/XXE/XSS/파일명/크기/PDF내장JS)을 **파서별 재증명** 필수(기존 zipGuard 자동 적용 가정 금지). + CJK 폰트 대체 취약 → 한글 깨짐 항목 추가.

## 실세계 잔여 리스크 로그
- **2026-07-21 (Phase 1 구현 종료 시점):**
  - 렌더 충실도 DoD 상태 = **UNVERIFIED**. real 코퍼스 0개(개발 환경에 개인문서 없음) < 최소 15개 → 규칙상 PASS로 부를 수 없음. 프로그래매틱 픽스처(PDF/DOCX)는 전부 readable이나 이는 회귀지표일 뿐 충실도 분모가 아님.
  - **잔여 리스크**: 실세계 파일(구형 익스포터, 폰트 서브셋, 한글 인코딩, 깨진 바이트)에서의 깨짐은 미검증. 해소하려면 UI-3(실 코퍼스 확보) 필요.
  - H1 판정: 개발자측(A) 데이터는 매우 유리(탭 2 / 셸 5.7KB / 로그인·광고·유출 0). 사용자측(B) 실기기·카톡 데이터는 미확보 → **H1 최종 판정 UNVERIFIED**, UI-2 프로토콜로 인계됨.
  - 보안 하드게이트 6종(sanitizer XSS·egress-0·zip bomb·XXE·PDF내장JS·파일명XSS)은 자동 테스트로 **전부 PASS**.
